## Capture and semantic learning

Learn offers **Record a little of my morning** on iOS 27 and **Choose a recording or file** on all supported platforms. Capture begins only after the person starts the flow and confirms Apple’s picker. The importer reads only the selected local file, uses security-scoped access while reading, samples at most 24 video frames, and uses Vision to extract visible text. Fast transitions may be missed; OCR does not provide a historical touch stream or establish why the user acted. The selected source file remains the user's file. The app does not keep exported sampled frames. [Vision text recognition](https://developer.apple.com/documentation/vision/recognizetextrequest).

The structured extraction retains every requested sample before notes deduplication, including blank/decode/OCR failures, exact actual timestamps where available and labeled fallbacks otherwise. Bounded OCR bodies, IDs and metadata—not frame pixels—are saved with each accepted acquisition. Optional line records preserve exact text and Swift Character ranges, local IDs, candidate confidence and approximate normalized lower-left bounds in the oriented image. These are neither exact glyph outlines nor tappable controls or app identities. Legacy layout remains `nil`; absent/invalid/capped geometry is not invented, and warnings identify omitted metadata. Existing OCR text order, trimming and newline joining remain unchanged before the normal extraction limits; only complete retained line spans survive clipping. Source-truncated or omitted text is marked and excluded from context identification.

Learn's optional **Recognize sampled screens** path selects an unchanged prefix of at most **320 characters and six whole nonempty lines** per eligible frame for separate bounded Foundation Models calls. The full source remains saved. Preparation policy `whole-line-source-prefix-layout-v2` may attach at most six matching line hints, with bounds/confidence rounded to six decimals, and records their IDs in optional `inputSelection` metadata. Exact stored geometry is unchanged. Hint size cannot displace a frame's selected text; optional hints are removed as needed before applying the single-prompt limit. Geometry never bypasses competing-header rejection or establishes an app identity. Accepted quotations must match UTF-8 bytes in both the supplied excerpt and original frame; visually identical Unicode rewriting is rejected. The earlier text-only pure preparation replay selected all **24 baseline samples and 2,217 characters**; that establishes input coverage, not correct recognition.

Unavailable, failed and completed-with-unknown outcomes remain distinct. The earlier Mac attempt reported model not ready with zero requests. The subsequent simulator attempt reported available but made **six failed requests, returned zero responses and retained 24 unknown decisions**. The app process's native log identified `operationNotAllowed: Simulator is not supported` in a required backend. This is a runtime support failure, not a finding that the content violated a policy or a model-abstention result. There is no physical-device context-model benchmark yet. [Benchmark evidence](OBSERVATION-BENCHMARK.md).

The OS 26 semantic path uses `SystemLanguageModel` and checks availability first. Capture/import/retry/reimport only saves or selects evidence. In Learn, **Confirm this observation** records a missing observed day, zone or activity origin; recording metadata does not establish human behavior, and import time does not supply the day. Saving that form performs no inference. The person then chooses **Suggest a routine** or **Suggest an update**, both using the same pending-proposal operation as saved-morning selection. Dynamic guided-generation schemas constrain the response; validation rejects unknown source units, unsupported categories, out-of-range durations and inexact quotations. Every accepted proposal remains unapproved and separate from the current routine until approval. Manual setup remains available when the model is unavailable. [SystemLanguageModel](https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel).

**Review → Saved observations → Choose mornings** prepares an update from one to five dated sources in the same time zone, all human observations or all synthetic samples; Learn uses its one selected acquisition. Corrections are labeled user reports; original video input retains eligible sampled-frame references and discloses exclusions. Each source must contribute eligible input, but a selection count does not establish support for every resulting step. Serial requests now process eligible input under per-request bounds; the earlier 8,000-character operation cutoff is historical. The resulting routine still has at most ten moments including preserved required rituals. These are bounds for reviewed proposals, not measured habit or time averages. [Learning and review contract](ROUTINE-LEARNING.md).

This update stays pending alongside the current routine until explicit approval. Its source and base-routine revisions are checked before saving, after restoration and before approval; source edits/deletion/date changes or base-routine changes invalidate a dependent proposal. Dismissal/relaunch preserves valid pending review; discard keeps the current routine. Approval saves a new approved version without starting it. The earlier saved-mornings slice at `4a2fd30` retains its separate results. The unified slice (`48e5c95`) passed 235 shared checks with six optional skips, the native simulator build and three UI journeys without skips: import preservation/relaunch, explicit provenance through pending approval/relaunch, and setup-only rejection. These used zero Apple model calls; real proposal quality remains unverified. Two further notice-review journeys passed across scoped runs after final routing changes. The unsigned iPhone build also passed; initial failures and corrected reruns remain in verification. Habit clustering, confidence tracking, contextual exceptions and continuous adaptation remain future work. No model-generated proposal is permission to perform an external effect.

### iOS 27 native recording

Apple now documents ScreenCaptureKit on iOS 27. Its sample presents `SCContentSharingPicker` for either the full display or the app's own content, then captures with `SCStream`. `SCRecordingOutput` encodes a recording to a file. A full-display stream surviving backgrounding uses the `screen-capture` background mode; microphone capture has its own audio-session/background requirements and follows the person's picker choice. The revised source implements a screen-only path with no microphone/camera, explicit Stop, selected 5/10/20/30-minute limits and a 256 MiB size bound. A shared owner survives dismissal of the app-owned Record/Learn sheets; a root status control remains. The Apple-owned picker/panel is distinct: automatic dismissal remains unverified, and no public dismissal API is established here. Finalized recordings are staged from the service callback; same-session clips proceed to local extraction while the foreground app is idle, whereas a pending clip recovered on relaunch requires Retry. The new flow opens saved-evidence review and requires an explicit suggestion after provenance checks; it does not automatically call the model. No separate Use action is normally required. Earlier XCTest and owner checks failed with an empty Learn field despite a success banner; those failures remain recorded in [PHASE-ONE](PHASE-ONE.md). A later owner-confirmed short clip on the historical phone build established capture → OCR → persisted text → visible unapproved draft, with readable text surviving ordinary-app relaunch. The draft incorrectly treated setup/marketing copy as habits. A subsequent deterministic filter replay rejects that known input; it is not a new model abstention or a general accuracy pass. Long captures, interruption/recovery, protected content and broad reliability still require their own device checks. This native path is not the iOS 26 baseline. [Apple's iOS screen-capture sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-on-ios).

Apple describes ScreenCaptureKit as the successor to ReplayKit for streaming/mirroring, without requiring a broadcast extension on its supported newer platforms. Do not carry forward a blanket claim that system-wide screen capture always requires a ReplayKit extension. Imported recordings remain the fallback on older supported systems. [ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit).

The workspace now keeps an acquisition archive and selected entry, capped at 60 entries with aggregate text, line-record and encoded-size limits. Readable imports add/select observations; blank imports leave earlier evidence intact. Corrections preserve original text and original frame/layout evidence but remove attached classification and invalidate dependent pending updates. Delete one/Delete all removes saved observation entries while retaining routines and their existing quotations. Pending typed citations are removed with approval, discard or invalidation; quotations embedded in an approved routine remain separately stored. Limits reject further additions rather than silently deleting older evidence; there is no automatic retention expiry. Simulator archive/import journeys at `d9a6120` have passing results across the original run and the targeted accessibility correction; physical recording provenance remains unverified. [Exact acquisition and retention limits](ARCHITECTURE.md#observation-acquisitions-and-dates).

Import time and observed day are separate. Native recording metadata retains the session ID plus the instant/time zone of the output-start callback through recovery; it does not claim exact first-frame alignment. Selected/legacy files stay undated until the person supplies an observed day, and origin remains unknown unless explicitly identified. Local streaming SHA-256 deduplicates identical file bytes while preserving existing corrections/dates; a second fingerprint before saving checks that extraction did not race a changed file. Hashes are not proof of authenticity, dates or human activity.

Owned raw media stays in the single RecordingRecovery slot after blank/OCR/cancellation/archive-save failure for Retry/Discard. It is removed only after the evidence archive and selection have reached the atomic workspace save, or after explicit discard. Recovery metadata contains an optional original start context and interruption note; old metadata remains valid with no context, and leftover metadata cannot date a later recording. A later model/classifier failure does not require the raw video. User-selected originals are preserved and no raw archive is added. Deleting observations does not discard a pending raw file; Discard recording does not erase saved evidence. Earlier storage/import checks remain narrower evidence; new archive integration checks and their corrected reruns are recorded in [PHASE-ONE](PHASE-ONE.md). Broad physical interruption/retry/discard reliability remains unverified.

Neither the importer nor this picker path is an automatic morning first-pickup detector, invisible continuous monitor, or global tap-event feed. DeviceActivity first-use scheduling and the newer entitled usage-data API are documented options in the [observation plan](OBSERVATION-PLAN.md), but neither is implemented.

## Siri, voice, and speakers

The start and quick-capture intents use `supportedModes = .foreground(.immediate)`, which requests foreground execution after the system resolves parameters. Start additionally requests local-device authentication and routes through the shared entry policy; it cannot approve a draft or repeat an already-running operation. A custom `@Parameter` String can collect capture text; Siri may ask for a missing value. App Shortcuts include the application-name token in trigger phrases. The source routes a capture to review and returns a “ready for review” dialog; it does not claim the text has already been durably saved. Keep that distinction if the design changes. [Intent modes](https://developer.apple.com/documentation/appintents/appintent/supportedmodes), [Creating an App Intent](https://developer.apple.com/documentation/appintents/creating-your-first-app-intent), [App Shortcuts guidance](https://developer.apple.com/videos/play/wwdc2025/244/).

The app bundle must contain discoverable intent metadata. A Swift type-check alone does not prove Siri registration. App-only foreground execution avoids an extension's separate process, but does not make in-memory state durable; the review flow still needs its explicit Save. If background extensions are added, use appropriate shared storage and process coordination. OS 27's `LongRunningIntent` can extend certain tasks with progress reporting; it is not an unlimited background agent or the baseline for this short capture flow. [Runtime behavior](https://developer.apple.com/documentation/appintents/configuring-the-runtime-behavior-of-your-app-intents), [Shared data](https://developer.apple.com/documentation/technologyoverviews/shared-data), [LongRunningIntent](https://developer.apple.com/documentation/appintents/longrunningintent).

The new **Log an app transition** intent uses background execution and writes a separate local journal. Users configure per-app Is Opened/Is Closed automations themselves; currently supported choices are Instagram, TikTok and Snapchat. Callback time, app, transition, time zone, source and event ID are recorded. A supplied stable UUID deduplicates a deliberate retry. The shared actor serializes same-process writes without replacing the workspace; actual background process behavior and delivery still need verification. This action does not start recording or read app contents. [Apple App triggers](https://support.apple.com/guide/shortcuts/setting-triggers-apde31e9638b/ios).

The app now has speech output and an explicit [push-to-listen command turn](VOICE.md). It checks `supportsOnDeviceRecognition`, requires local recognition, displays transient text and accepts one final strict English/French command only after microphone release. It saves neither microphone audio nor the command transcript, and does not fall back to server recognition. This is source plus simulator entry/cancel evidence, not a real microphone trial or continuous conversation. Siri's own input path is separate and controlled by the system; local app storage does not imply every Siri request is processed offline. [Speech availability](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition), [On-device recognition requests](https://developer.apple.com/documentation/speech/sfspeechrecognitionrequest/requiresondevicerecognition).

On iOS the app exposes a real `AVRoutePickerView`; the user selects an available output. There is no active Mac app workflow. AirPlay can deliver media to compatible speakers, but output routing is separate from input capture and does not establish access to a HomePod microphone. The route, audible result and behavior after disconnection still need a physical test. [AVRoutePickerView](https://developer.apple.com/documentation/avkit/avroutepickerview), [Supporting AirPlay](https://developer.apple.com/documentation/avfoundation/supporting-airplay-in-your-app).

Automatic room detection, person tracking and room-to-room transfer are not implemented. HomePod's documented cloud media integration targets media services and is not a generic microphone API for this app. [SiriKit Cloud Media](https://developer.apple.com/documentation/sirikitcloudmedia).

## EventKit permission and effect boundaries

Calendar reading requires full access; creation can use write-only access. Reminders uses full access for both reads and writes. Required purpose strings are `NSCalendarsFullAccessUsageDescription`, `NSCalendarsWriteOnlyAccessUsageDescription`, and `NSRemindersFullAccessUsageDescription` according to the enabled flow. Sandboxed macOS EventKit builds also need the calendars personal-information entitlement. [Event-store access](https://developer.apple.com/documentation/eventkit/accessing-the-event-store).

`ReminderService` never requests permission inside a read or create method. Its explicit permission methods must be called by the app's user-driven flow. Draft validation occurs before writes. New events have no recurrence, attendees or invitations; reminder alerts are explicit draft values. Reminder due components use a Gregorian calendar and the chosen time zone. [Creating events and reminders](https://developer.apple.com/documentation/eventkit/creating-events-and-reminders), [Reminder due components](https://developer.apple.com/documentation/eventkit/ekreminder/duedatecomponents).

The app retains a successful write receipt to prevent an ordinary retry from creating the same item again. A crash between the system write and local receipt persistence remains a recovery boundary: inspect Calendar/Reminders before retrying an uncertain effect. An EventKit success reports a local system-store save, not proof that a cloud account has completed syncing or that an alert was heard. Content deliberately saved to those apps follows their configured accounts and sync policies.

The date parser recognizes a limited grammar. “Tomorrow morning” means a proposed 09:00 on the next local calendar day; “in four hours” means four elapsed hours. Unsupported or ambiguous recognized expressions remain unresolved. The parser retains the original in its transient parse result; the saved capture contains the text the person reviewed and saved. The user can edit the proposed time or keep a reminder undated; there is no silent universal language/date understanding.

## Evidence and future analytics

The existing day/week history measures runs inside Morning Operator. The separate App activity view in Review summarizes callbacks from configured apps, including returns after another tracked app. It is not integrated into a seven-day external-app usage model and has not been validated on a configured phone. Missing callbacks/unconfigured apps can hide intermediate activity; entry counts are not pickups or measured duration. The setup sheet now offers Clear recorded app activity; installed-device verification, export and automatic retention limits remain pending. Disabling Shortcuts automations stops future callbacks rather than removing saved entries.

Routine history remains distinct from these callback counts. Synthetic runs are excluded from personal averages; interrupted timing is unknown rather than guessed. The core data model can hold app observations with evidence references, coverage and optional counts, but the recorder does not yet populate a longitudinal per-app analytics store. A visible message does not prove the user read it, and OCR alone does not establish an exact reel, like or swipe count.

The `ObservationVideoEvidence` adapter preserves frame order and validates identity decisions before producing `ObservationTrace`. Learn shows the selected acquisition's recognized appearances, not measured app entries: generic headers can change within one app. The app leaves continuous capture coverage undeclared, so media duration does not become actual usage or a sampled-time estimate. The new archive retains separate observations for date-based review; comparable-day reports preserve unknowns and per-metric denominators, but no observed-habit average is wired into history. [Metric definitions and implementation boundary](OBSERVATION-METRICS.md).

[Issue #21](https://github.com/gibouu/morning-operator/issues/21) covers timestamped extraction, day/week aggregation, corrections and uncertainty. No sale, export pipeline, tracking SDK or third-party analytics collection is implemented. Any future aggregate-data product is a separate product/consent decision; raw recordings, private messages and HealthKit data are not a monetization feed in this prototype.
