## Product and workload assumptions

The primary job is a personal morning that the owner explicitly teaches, reviews, approves and runs, preserving useful rituals and reducing phone handling. `README.md:7–17` states that loop; `Sources/MorningCore/RoutineSession.swift:50–57` (`startRefusal`) enforces approval and valid steps. A proposed activation criterion is **one real observation leads to a reviewed, approved routine and one successfully completed owner-run morning**. An install or synthetic sample does not establish that outcome.

No measured latency, battery, memory, archive-growth, RTO or RPO targets were established here. Relevant units are **per-device source requests, OCR frames, model calls, bytes saved and successful mornings**, not server RPS/customer counts. There is no shared application backend, SQL pool, web tenant store, queue server or CDN in the inspected runtime/configuration; those audit subchecks are not applicable. Apple/Google provider quotas and device resources still matter.

## Architecture, threading and critical flows

```text
SwiftUI / MorningStore (@MainActor; UI/session coordination)
    -> MorningCore (validated domain values/state machines, persistence/privacy gate)
    -> MorningApple (EventKit/WeatherKit/OAuth/media/model/Activity adapters)
         -> Apple frameworks / explicit Google HTTPS requests
    -> app-owned Application Support JSON + owned recovery media
    -> Keychain refresh credential only

Activity widget -> bound intent in app process -> small persisted timer
AlarmKit owns alarm schedule -> authenticated foreground intent -> guarded app entry
```

`Package.swift:9–21` separates Core, Apple and unlinked Health modules; `project.yml:24–73` separates the app and widget. The ordinary app does not link UI-test phone control (`project.yml:74–90`). `MorningStore` is main-actor isolated (`Sources/MorningOperator/MorningStore.swift:120`); model/UI coordinators also use the main actor. OCR/file extraction uses `MediaObservationService` actor (`Sources/MorningApple/MediaObservationService.swift:55`); selected routine-file import uses a detached, cancellation-linked bounded reader (`Sources/MorningApple/RoutineDocumentReader.swift:9–55`). Actor isolation prevents data races only within its contract: it does not make synchronous JSON encoding/file I/O cheap or eliminate stale results across an `await`.

**Read — Gmail:** `GmailConnectionView` restores on appear/active and clears volatile data on disappear/background (`Sources/MorningOperator/GmailConnectionView.swift:31–45`). The controller captures privacy state/attempt, silently restores a saved credential, then reads the count and a bounded header list (`Sources/MorningOperator/GmailConnectionController.swift:104–143`). The service validates the refresh grant and expiry, uses fixed Google URLs and a read-only scope, then requests count → list → at most 5 metadata GETs (`Sources/MorningApple/GmailConnectionService.swift:287–343,400–479`). Each publication rechecks attempt and privacy generation (`Sources/MorningOperator/GmailConnectionController.swift:336–342`); partial header failure is reported, while cancellation or authorization failure aborts (`Sources/MorningApple/GmailConnectionService.swift:428–449`). Close/background cancels and clears content (`Sources/MorningOperator/GmailConnectionController.swift:247–263`). A selected message is displayed as plain text. No send action exists in this read path.

**Write — approve a routine:** `Sources/MorningOperator/MorningStore.swift:571–589` (`approve`) checks privacy, routine, busy/session and saved-choice state, constructs an approved version and session, then calls `persist`; failed persistence restores the previous in-memory routine/session and returns false. In the same file, `persist:2202–2256` refuses unreadable workspace recovery, invalidates stale derived proposals, takes `LocalDataControl.withReadyAccess`, writes the full snapshot, then publishes success. `AtomicJSONFile.save` encodes and stages an owner-only sibling file, synchronizes it and atomically renames it (`Sources/MorningCore/Persistence.swift:50–85`). It provides atomic replacement; it does not provide a transaction across all app/system stores or guarantee sudden-power-loss durability. Sessions pin approved immutable routine versions and validate restored event replay (`Sources/MorningCore/RoutineSession.swift:25–33,45–57,84–100`).

**Background — target timer and alarm:** `beginTargetStep` saves an absolute timer/open marker before an external handoff, preventing a routine reopen from silently dispatching the same target again (`Sources/MorningOperator/MorningStore+StepTimer.swift:19–49`). Timer mutations are load/change/save without suspension under the shared privacy file lock; +2 publishes only after successful save (`Sources/MorningApple/StepTimerRuntime.swift:15–75`). Native notification operations are revision checked and serialized (`Sources/MorningApple/StepTimerRuntime.swift:97–128,196–210`). The notification add uses `try?`, leaving no failure diagnosis at that call site; inspection does not prove delivery. Deadline arrival does not automatically advance. A background target budget continues, while ordinary narration pauses (`Sources/MorningOperator/MorningStore+StepTimer.swift:14–16`; `Sources/MorningOperator/MorningRootView.swift:173–182`). Alarm Save persists its identity before awaiting the system schedule and reconciles after restart/permission changes (`Sources/MorningOperator/MorningAlarmService.swift:46–87,91–146`). AlarmKit owns delivery. The alarm's Stop and Start MORE currently share the same start intent (`Sources/MorningOperator/MorningAlarmService.swift:124–134,159–170`), a product semantics decision to confirm.

## Material findings and bounded next actions

**IOS-01 · Decide recovery retention targets · P2 · high confidence about current behavior · investigation.** If processing fails and the owner never returns, app-owned recovery can remain until explicit Retry/Discard/Forget. No agreed expiry duration was established in this audit, so this is a product/privacy decision before it is an implementation defect. Existing generation/reset and save-dependent raw deletion are counter-evidence to any claim of indiscriminate retention. The smallest next step is owner-approved durations and category-specific retention/deletion acceptance; any implementation can then extend the existing lifecycle. Owner: privacy/storage; implementation effort depends on the selected policy. Proposed verification covers synthetic interrupted capture/save/cancel/expiry and retained-quotation behavior. It does not require deleting real evidence. Link existing #8 rather than duplicate it.

**IOS-02 · Establish a resource envelope before scaling learning/storage · P2 · medium confidence · investigation.** The baseline accepts large archives, rewrites a full workspace synchronously on main actor, and permits up to 768 serial local model calls. These facts create a plausible hitch/energy/long-wait risk, not a proven hang. The smallest next step is agreed representative/max synthetic fixtures and authorized Instruments/main-thread/file-activity measurements, plus cancellation/low-storage cases. Owner: iOS performance/model; measurement scope and fix effort are conditional. Record hardware/OS, bytes, p50/p95 save/launch, model duration, peak memory, energy/thermal state and retained data. Any change must preserve serial commit/generation semantics. Actor isolation alone does not ensure responsive UI if the UI waits on blocking work.

**IOS-03 · Establish backup/restore and upgrade behavior · P2 · high confidence about evidence gap · investigation.** Routine export deliberately excludes the evidence/history that a returning owner may value; recovery and privacy are separate files/system stores. Refusing unsupported files protects their contents, but does not recover device loss or prove old/new schema compatibility. Owner: persistence/release; start with a scoped synthetic restore/upgrade plan; implementation is conditional. Define what may be lost and how quickly manual recovery must work. Proposed verification covers same/new-device restore and old/new builds in isolation. Preserve originals on unsuccessful upgrades; local Forget does not erase external backup copies.

**IOS-04 · Define privacy-safe operational evidence · P2 · medium confidence · investigation.** The inspected logging does not establish alarm/timer delivery, morning completion success, failures by release or local performance. First investigate notification-add error visibility and how the owner requests support. Candidate signals are redacted error classes/timing, a local diagnostic/export opt-in or Apple aggregate tools, plus a named maintainer. An automatic upload pipeline is not required. Owner: iOS/operations; scope follows the privacy and ownership choices. Acceptance: diagnose a controlled synthetic source/timer/save failure without message, recording, credential or URL content.

**IOS-05 · Reconcile current navigation/release guidance · P2 · high confidence · observed baseline gap.** A teammate following the baseline README can use obsolete navigation and accidentally overstate older proof. Owner: integration/docs; this documentation track addresses the guidance, while device release acceptance remains separate. Keep source behavior and dated evidence authoritative, compare other branches/PRs before selecting changes, update the baseline, then complete one ordinary-app rehearsal. An open issue alone does not justify merging an older track wholesale.

Immediate sequence: (1) freeze the exact ordinary-app promise and branch overlap; (2) reconcile current guidance; (3) agree retention/recovery targets; (4) authorize bounded resource/restore/adverse-case verification; (5) finish one normal owner-run end-to-end release rehearsal with explicit unsupported slots. The shared demo-specific scope and transitions are in [DEMO-REQUIREMENTS](../DEMO-REQUIREMENTS.md) and [DEMO-TEST-PLAN](../DEMO-TEST-PLAN.md).
